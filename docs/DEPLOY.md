# Деплой на Fly.io

Усе, що нижче, виконується з вашої машини: потрібен обліковий запис Fly
і встановлений `flyctl` (`curl -L https://fly.io/install.sh | sh`).

## 0. Важливо перед початком

Команди виконуються **у теці проєкту**, а не в домашній: без `fly.toml`
поруч `flyctl` не знає, який застосунок має на увазі.

```
git clone https://github.com/kovalenkoserhii2107-maker/psykovalenko.git
cd psykovalenko
```

І не додавайте до команд коментарі через `#`: zsh у macOS за замовчуванням
не вважає це коментарем і передає решту рядка як аргумент.

## 1. Створити застосунок

```
fly auth login
fly launch --no-deploy --no-db --copy-config
```

`--copy-config` бере наявний `fly.toml`, `--no-db` не дає майстрові
створити базу самому — її створимо наступним кроком.

Якщо оберете інше ім'я застосунку, виправте `app` і `NEXT_PUBLIC_SITE_URL`
у `fly.toml`.

## 2. База даних

Fly більше не підтримує стару некеровану Postgres — беремо керовану:

```
fly mpg create
fly mpg attach --app psykovalenko
```

`attach` сам пропише секрет `DATABASE_URL`. Міграції накочуються
автоматично перед кожним деплоєм — це `release_command` у `fly.toml`.

## 3. Диск під вкладення

Спершу подивіться, у якому регіоні насправді створено застосунок —
майстер `fly launch` міг запропонувати інший:

```
fly status
```

Далі створіть диск у тому самому регіоні (підставте свій замість ams):

```
fly volumes create psy_data --size 1 --region ams
```

На питання «Do you still want to use the volumes feature?» відповідайте
латинською `y`: кирилична «т» не приймається, і диск не створиться.

Без диска файли домашніх завдань зникнуть при першому ж перезапуску
машини, а деплой упаде на монтуванні.

## 4. Секрети

```
fly secrets set AUTH_SECRET="$(openssl rand -base64 32)"
fly secrets set AUTH_URL="https://psykovalenko.fly.dev"
```

`AUTH_URL` має точно збігатися з адресою сайту, інакше вхід кидатиме
на неправильний домен.

За потреби — ключі інтеграцій:

```
fly secrets set ANTHROPIC_API_KEY="..."
fly secrets set AUTH_GOOGLE_ID="..." AUTH_GOOGLE_SECRET="..."
```

## 5. Деплой

```bash
fly deploy
fly open
```

## 6. Створити обліковий запис психологині

Пароль задається один раз, із вашої машини через тунель до бази:

Лишіть відкритим в окремому вікні:

```
fly mpg proxy
```

У другому вікні, у теці проєкту (адресу бази показує `fly mpg status`):

```
DATABASE_URL="<адреса з fly mpg, але з localhost і портом проксі>" ADMIN_EMAIL="kovalenkotanya2205@gmail.com" ADMIN_PASSWORD="<довгий пароль>" npm run db:seed
```

## 7. Свій домен

```
fly certs add psykovalenko.com
```

Далі Fly покаже, які A/AAAA записи прописати в реєстратора. Після того як
домен запрацює, змініть у `fly.toml` `NEXT_PUBLIC_SITE_URL`, оновіть секрет
`AUTH_URL` і задеплойте ще раз — обидві адреси зашиті в збірку й у сесії.

## Після першого вдалого деплою

Статичний лендинг у корені репозиторію (`index.html`, `assets/`, `.nojekyll`)
більше не потрібен: його роль виконує сам застосунок. Тоді ж можна вимкнути
GitHub Pages, щоб не лишалося другої, застарілої копії сайту.

## Якщо база й застосунок у різних регіонах

Це не помилка, але кожен запит ходитиме між дата-центрами. Перевірити:
`fly status` покаже регіон застосунку, `fly mpg list` — регіон бази.
Щоб звести їх разом, простіше перестворити застосунок у регіоні бази.

## Чого я не перевірив

Образ не збирався: у середовищі, де писався код, немає демона Docker.
Перевірено інше — що збирається сам застосунок (зокрема послідовність
prisma generate → next build, на якій падав перший деплой), що міграція
накочується на чисту базу окремим деревом Prisma CLI — так само, як це
робить release_command, — і що standalone-збірка стартує, віддає сторінки,
статику й ходить у базу.

Якщо `fly deploy` упаде — надішліть останні рядки логу.
